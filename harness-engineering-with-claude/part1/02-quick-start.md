# 30분 Quick Start

읽기만 하지 말고, 직접 하나씩 따라해보며 같은 프롬프트를 하나는 하네스 없이, 다른 하나에는 하네스를 적용한 결과물들을 비교하고 교훈을 얻어보자.

## 학습 목표

하네스가 '좋은 프롬프트'와 어떻게 다른지 결과물로 직접 보고, .claude/agents/와 .claude/skills/ 디렉터리를 처음부터 만들어 보자.
author와 reviewer 두 에이전트가 파일을 주고 받으며 협업하는 2인 팀을 완성하고, 자연어 한 줄로 팀을 소환하는 경험을 한다.

## 핵심 키워드

- 에이전트 정의 파일
- 스킬 파일
- 생성-검증 패턴
- CLAUDE.md
- 자연어 트리거
- 파일 기반 협업

## 내용 전개 및 요약

### 직접 해보는 것의 중요성

- [step 1] 5분, 눈으로 확인
  - 같은 프롬프트, 다른 산출물
  - "Claude code 사용 팁을 정리해 주세요" 라는 프롬프트 한 줄을 에이전트에게 실행 시켰을 때
  - A.하네스 미적용 B.하네스 적용 두가지 비교군을 갖고 진행한 실험을 표로 정리함(39p)
- [step 2] 30분, 손으로 확인
  - 2인 팀 만들기를 가지고 간단히 실습
  - 이 step 2에서 기억할 것은 "파일이 없으면 존재하지 않는다." 라는 것
  - 에이전트는 반드시 `.claude/agents/{name}.md`로, 스킬은 `.claude/skills/{name}/SKILL.md 파일로 정의되어야 함
  - 에이전트와 스킬은 한 번 쓰고 버리는 일회용이 아니라, 저장소에 들어가 계속 운용되는 자산
  - 두 디렉터리는 각각 "누가 할 것인가" 와 "어떻게 할 것인가"를 정의한 공간이라 할 수 있음

### step 2 진행 설명

author 에이전트가 커밋 메시지 초안을 `_workspace/commit-draft.md`에 작성하면, reviewer가 그 파일을 읽고 PASS 또는 REDO 판정.

이를 **생성-검증 패턴**의 가장 작은 형태로써 구성하여 한쪽이 놓친 문제가 있다면 다른 쪽의 기준에서 걸릴 가능성을 높이는 것.

한편, 마크다운 내 프론트매터를 정의할 때 에이전트의 도구 필드는 tools이고, 스킬은 allowed-tools임.

> 프론트매터란 마크다운 파일 최상단에서 ---로 감싸 작성하는 YAML 형식의 설정 블록. 클로드 코드는 이 블록 읽어서 판단 후 적절히 작업 수행함

#### 1. 프로젝트 스켈레톤

step 2 구성:
`md
    my-first-harness/
    ├── .claude/
    │   ├── agents/
    │   │   ├── commit-msg-author.md
    │   │   └── commit-msg-reviewer.md
    │   └── skills/
    │       └── commit-message/
    │           └── SKILL.md
    ├── _workspace/
    └── CLAUDE.md
   `

#### 2. 생성·검증 2인팀

에이전트 md 파일 본문 세 블록의 역할

- 핵심 역할: 에이전트가 수행해야 할 작업을 번호 순서로 나열
- 작업 원칙: 선택지가 충돌할 때 어느 쪽을 택할지.
- 입출력 프로토콜: 무엇을 받아서 무엇을 내놓는지를 명확히 정의.

#### 3. commit-msg-author 에이전트 작성

커밋 메시지 작성자 역할을 맡을 에이전트. 프로젝트의 커밋 스타일에 맞는 커밋 메시지 초안을 자동으로 작성하는 테스크 담당.

#### 4. commit-msg-reviewer 에이전트 작성

author가 초안을 만들었다면, 그 초안이 실제로 쓸 만한지 검토하는 역할.

이 파일에서 반드시 포함해야 할 규칙은 두 가지

첫째, PASS/REDO 판정 기준을 명확히 정의해야 함

- '형식을 어긴 경우'와 '사실과 다른 내용이 있는 경우'에만 REDO 내리도록 객관적 기준을 못 박아둬.
- 이 기준이 없다면 클로드가 매번 다른 판단을 내릴 수 있음

둘째, 반복 횟수에 상한을 설정해야 함

- 종료 조건 없이 이어지면 에이전트가 멈추지 않아 종료 규칙 마련해야.

> 실무에서는 판정을 3단계로 나누어 FIX 같은 중간 판정을 하나 더 두는 경우가 많음

#### 5. commit-message 스킬 작성

개발자가 자연어로 커밋 메시지 작성을 요청하면 클로드가 이 스킬을 찾아 실행함.

- description은 공격적으로 쓰기
  - 스킬은 자연어 트리거로 발동하기 때문에 모호하면 스킬이 호출되지 않는 경우가 생김. 이 파일에서 쓴 description은 크게 세가지로 구성됨
  - 동사: 무엇을 하는가
  - 상황: 언제 호출하는가
  - 경계: 언제는 해당하지 않는가
- allowed-tools vs tools
  - 필드명 오탈자는 에러 메시지 없이 실패하기 때문에 가장 주의 필요!
  - 더 엄격하게 권한을 제한하고 싶다면 Bash(git diff.\*)처럼 인자 패턴까지 지정할 수 있음
- workflow: 번호 매김만으로 두 에이전트를 조율함
  - workflow는 5단계로 구성됨. 여기서 주목할 점은 별도의 오케스트레이션 도구 없이, 본문의 번호 매김만으로 두 에이전트를 순차 호출한다는 것
  - TeamCreate, TaskCreate 같은 고급 조율 도구 없이도, 이 스킬 하나로 전체 흐름이 작동함
    -> 이게 2인 팀 구성의 장점

#### 6. 첫 실행 - 자연어 한 줄로 팀 소환

책에서는 간단하게 README 수정하고 진행.

에이전트들이 대화가 아니라 **파일을 통해** 소통함을 알 수 있음

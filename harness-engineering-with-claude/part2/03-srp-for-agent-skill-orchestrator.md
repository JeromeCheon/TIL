# 에이전트·스킬·오케스트레이터의 책임 분리

## 시작하면서..

한 에이전트에 생성·검증·조율 다 몰아넣으면 처음에야 편해보이지.
시스템이 커질 때는 한 부분을 고치면 다른 부분이 깨지기 쉬워.

## 학습 목표

에이전트, 스킬, 오케스트레이터 각각의 역할과 경계를 이해하고 책임이 뒤섞였을 때 나타나는 다음 네가지 문제를 파악함

- 재사용 불가
- 병렬화 불가
- 누락 반복
- 컨텍스트 폭발

## 핵심 키워드

- 에이전트
- 스킬
- 오케스트레이터
- 관심사 분리
- 책임 매트릭스
- 단일 책임 원칙

## 줄거리 요약 및 정리

### 2인 팀을 분해해보자

파트 1에서는 '왜 하네스인가?'를 다뤘다면, 여기서는 '어떻게 구성하는가'를 중점적으로 다룬다.

이 장의 핵심은 다음 한 문장으로 정의할 수 있고, 이는 클로드 코드 공식 내부 문서에도 있는 내용을 조금 다르게 해석한 부분이다.(작업;Task를 독립적으로 두지 않고 오케스트레이터 내부 도구로 재배치)

> 하네스는 누가(Agent), 어떻게(Skill), 언제·누구와(Orchestrator)라는 세 가지 요소로 나뉘며, 이들은 독립적으로 설계되고 실행 시점에만 맞물린다.

### 한 파일에 다 넣으면 무엇이 깨지는가

part 1에서의 commit 에 대한 author·review 에이전트들을 "commit-master"라는 하나의 에이전트로 통합을 했다고 가정하자.
그랬을 때 문제는 다음과 같다.

1. **재사용 불가** : 커밋 형식 체크 로직을 PR 리뷰용 에이전트에서도 쓰고 싶다면 복붙밖에 없어. 한 쪽을 고치면 다른 쪽을 고쳐야 하고, 그러다 일관성이 흐트러지게 돼.
2. **병렬 불가** : '생성', '검증'이 한 에이전트 안에 있으면 병렬 실행이 불가. 각각 다른 에이전트에게 할당하면 가능해지지.
3. **누락 반복** : 단일 에이전트의 자기 검증 실패 모드가 그대로 반복돼. 한번 누락하거나 틀리면 그대로 가게 되는 문제.
4. **컨텍스트 폭발** : 역할 설명, 판정 기준, 형식 지식, 호출 순서, 에러 정책 등이 한 파일에 쌓이면서 어느새 수백 줄이 넘는 복잡한 파일이 되어 버려.

한 마디로, 관심사가 하나로 섞이게 되는데 이를 **누가·어떻게·언제 누구와 를 분리함**으로써 해결 해낼 수 있음

### 세 가지 핵심 요소

이 장에서는 경계선만 명확히 하고자 함

#### 1. Agent - 누가

에이전트 정의 파일은 단순한 설정 파일이 아니라, "역할 계약서"임.
뭘 담당하고, 어떤 기준으로 판단하며, 누구와 어떻게 소통하는지를 명시한 살아있는 문서

#### 2. Skill - 어떻게

워크플로, 트리거, 절차적 지식이 스킬의 영역.
에이전트가 세션간 재사용되는 역할 자산이라면, 스킬은 세션간 재사용되는 절차 자산.

ch2 의 `commit-message` skill 처럼, "Precondition 체크 -> author 호출 -> reviewer 호출 -> PASS/REDO 분기 -> 최대 2회 재호출" 명시 절차 방식

#### 3. Orchestrator - 언제·누구와

팀 구성, 작업 의존성, 단계 전환이 오케스트레이터의 영역.
이 요소는 위 둘과는 다르게 _영속 파일 하나로 고정되지 않는다._

오케스트레이션은 주로 실행 흐름을 담고 있기 때문에 사용자 요청이 들어오면 세션 안의 메인 루프가 팀을 구성하고, 단계를 전환 하고, 팀을 해체해. 규칙 자체는 스킬 본문이나 CLAUDE.md에 기록 될 수 있으나, 그 실행자는 런타임의 메인 루프.

> 오케스트레이터는 지시자가 아니라 지휘자야. 팀원 각자가 자신의 악기를 연주하도록 맡겨 최고의 연주를 만들어 내는거지.

#### 4. 왜 작업(Task)이 아니라 오케스트레이터인가?

한 분석 자료(클로드 코드 원문)는 클로드 코드를 에이전트, 스킬, 작업 이렇게 세 시스템으로 분석하지만, 이 책에서는 Task를 독립적인 요소로 안 두고 오케스트레이터 내부 도구로 재배치했어. 이유는 아래 세가지.

- Task 는 조율의 수단이지, 독립된 관심사 x
  - `TaskCreate` 같은 기본 도구는 오케스트레이터가 "A에게 이걸 시키고 B는 그다음에 실행해라"를 기록하는 수단
  - 도구에 불과한 걸 기둥으로 올리면, 같은 내용을 다른 이름으로 두 번 쓰는 셈
- 기록 구조의 설계 책임은 오케스트레이터에 있음
  - 작업 장부에 내용을 적는 건 팀원이지만, 이 장부 자체를 만들고 언제 열고 닫을지 결정하는 건 오케스트레이터
- 기준이 셋일 때 가장 기억하기 쉬움
  - 이건 실용적인 이유 때문인데, 4가지 보다 3가지로 정리하는게 쉽고 기억에 잘 남기에

> 저자는 클로드 코드 원문이 틀린게 아니라, 관점의 차이라고 어필함. 클로드 코드의 시스템 정의는 **실행 관점**이고, 이 책에서는 **책임 관점**으로 나눈다는 것

#### 세 가지 핵심 요소가 섞이면 생기는 문제

세 가지 중 하나가 다른 요소의 일을 맡기 시작하면 어떤 문제가 생기는지 아래 네 가지 패턴을 점검 해보자.

**안티패턴**

1. 에이전트 한 명이 모든 역할을 다 맡는다.
   - 예시: `super-dev.md` 같은 에이전트 하나에, "기획, 코딩, 리뷰, 배포" 등 역할을 OR로 줄줄이 연결해서 정의
   - 문제점:
     - 처음 놓친 문제를 다시 놓쳐
     - 재사용이 막히고 제한적이게 돼
     - 고치기 어렵고, 권한이 과도하게 늘어나서 최소 권한 원칙이 깨져

2. 스킬이 팀 전체를 지휘하려 한다.
   - 예시: 스킬 본문에 "조건 A면 에이전트 X를 부르고, B면 Y를 부르고, 그 사이에 사용자에게 확인을 받고..."가 많은 단계 넘게 이어지는 상황
   - 문제점:
     - 팀 구성, 단계 전환, 에러 복구까지 넣으면 스킬 본연의 정체성을 잃게 돼
     - 다른 팀 구성에서 이 스킬을 재사용하려 해도, 오케스트레이션 로직이 뒤엉켜 있어서 떼어내기가 쉽지 않음
   - 예외:
     - 오케스트레이션 자체를 목적으로 만든 메타스킬은 다름
     - 구분 기준은 간단한데, 스킬 주어가 '절차'라면 분기는 가볍게 두고 조율은 밖으로 빼. 스킬의 주어가 '팀 조율'이라면 Phase를 직접 선언해도 돼

3. 리더가 직접 일을 처리한다.
   - 내용: 리더 에이전트가 팀원에게 시키지 않고 직접 diff를 읽고, 직접 리뷰를 쓰고 직접 수정함. 6장에서 다루는 '우체국 안티패턴'
   - 문제점:
     - 팀원이 네 명 있어도 모든 정보가 리더를 거쳐야 한다면 팀원들은 서로의 존재 모른 채 갇혀 있는 것과 다름없어
     - 이렇게 되면 팀은 그저 순서대로 실행되는 파이프라인이 되어 병렬 실행의 이점 즉 팀 협업 이점이 사라져
     - 이는 리더 컨텍스트 한계를 초과하며 자신이 병목이 되는 것

4. 에이전트 파일에 절차 지식을 다 넣는다.
   - 내용: 에이전트 정의 파일이 500줄을 넘는다; convention을 이렇게 작성하며, 보안 취약점 유형 체크, 리뷰 코멘트 템플릿 예시 20개 등이 통째로 들어가 있다면?
   - 문제점:
     - 절차적 지식은 여러 에이전트가 재사용 할 수 있는 자산이기에, 따로 넣어두면 두 파일이 다르게 수정되거나 기준이 엇갈려
   - 해결방법: 공통 지식 스킬 분리

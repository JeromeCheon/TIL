# 에이전트를 정의한다는 것

## 학습 목표

에이전트 정의 파일을 '설정 파일'이 아닌 '역할 계약서'로 바라보는 관점을 갖고,
name·description·model·tools 필드와 본문 7섹션을 올바르게 채우는 방법 익힘.

또 어떤 모델을 고를지, 어떤 도구를 허용할지를 결정하는 기준도 함께 살펴봄

## 핵심 키워드

- 에이전트 정의 파일
- 역할 계약서
- 프론트매터
- description 작성법
- tools 최소 권한
- 입출력 프로토콜
- 팀 통신 프로토콜

## 줄거리 요약 및 정리

### 어제 잘 굴러가던 팀이 오늘 갑자기 사라지는 이유

에이전트는 구두로 존재할 수 없고 파일로만 존재해.

하네스에 익숙하지 않는 개발자들은 '파일 대신 에이전트 도구(클로드 코드가 제공하는 서브에이전트 호출 도구)의 프롬프트 인자에 역할을 직접 써 넣으면 되는 것 아닌가?' 라고 생각할 수 있어.

이 생각은 다소 위험한데, 우리가 직원을 채용했을 때 첫날 그 직원에게 구두로 이런 이런 것들을 알려줘도 그 직원은 이를 대부분 까먹고 출근할 것.
에이전트도 마찬가지야. 세션이 끝나면 아무것도 기억하지 않으며, 프롬프트 파라미터에 값을 직접 넣는 방식은 그 세션에서만 유효해.

이러면 문제는 다음 세가지로 정리돼.

- 다음 날 다시 팀을 소환할 때 역할을 처음부터 다시 설명해야 함
- 두 세션이 같은 기준으로 판단했는지 검증할 길이 없음
- 팀 멤버가 늘면 누가 무엇을 하는지 설명을 계속 반복해야 함

이 장의 목적은 "파일이 없으면 존재하지 않는다."라는 원칙이 만들어 내는 실무 결정을 에이전트 파일 하나 안에서 처리하는 방법을 배우는 것.

- 프론트매터 5개 필드: name·description·model·tools·선택 필드
- 본문 7개 섹션: 핵심 역할·작업 원칙·입출력 프로토콜·팀 통신 프로토콜·에러 핸들링·협업·품질 자체 검증

#### 에이전트 정의 파일 = 역할 계약서

'설정' 보다 '계약서'가 정확한 이유는 간단해.
설정 파일은 값을 저장하지만 계약서는 약속을 저장함. description 한 줄이 호출 시점을 바꾸고 tools 한 줄이 부작용 범위를 바꿈. 이 한 줄이 판정 기준과 권한을 동시에 바꾸므로 계약서라고 인식하는게 타당해.

프론트매터 -> 호출자에게 보이는 부분
본문 7개 섹션 -> 에이전트 자신이 참조하는 면

프론트매터가 명함이라면, 본문은 그 에이전트가 일하는 방식을 담은 내부 지침서

### 본문 7개 섹션 - 왜 필요하고 어떻게 쓰는가

각 섹션을 '왜 필요한가 -> 나쁜 예 -> 좋은 예' 순서로 살펴보면 다음과 같음

#### 1. 핵심 역할 - 범위 결정

하는 일을 1~3개로 명시하는 것은 곧 **하지 않는 일도 함께 경계 짓는다** 를 뜻함

- 나쁜 예

```md
## 핵심 역할

- 세계관을 만든다.
```

- 좋은 예

```md
## 핵심 역할

1. 세계의 물리 법칙과 기술 수준 정의
2. 사회 구조, 정치 체계, 경제 시스템 설계
3. 역사적 맥락과 현재 갈등 구조 수립
4. 장소별 환경과 분위기 묘사
```

이렇게 구체적으로 나열했을 때 에이전트는 세계관 설계할 때 캐릭터를 설계하거나 플롯을 구성하지 않아. 이는 다른 에이전트를 정의하고 위임하는 기반이 돼.

#### 2. 작업 원칙 - 판단 기준 결정

두 선택지가 충돌할 때 어느 쪽을 택할지 알 수 있어야 함. 원칙이 추상적이면 실행할 때마다 결과가 달라져.

- 나쁜 예

```md
## 작업 원칙

- 최선을 다한다.
- 품질을 높인다.
- 빠르게 작업한다.
```

- 좋은 예(webtoon-reviewer)

```md
## 작업 원칙

- PASS/FIX/REDO 3단계로 명확히 판정
- FIX는 부분 수정으로 해결 가능한 경우, REDO는 전면 재생성 필요
- 주관적 취향이 아닌 객관적 기준(일관성, 가독성, 구도)으로 판단
```

좋은 작업 원칙은 세 가지 조건을 만족함

- 두 선택지 앞에서 어느 쪽을 택할지 알 수 있어야 함
- 규칙의 이유가 담겨야 함
- 이 에이전트만의 특성을 드러내야 함. 일반론으로 채우면 다른 파일과 복사-붙여넣기가 됨

#### 3. 입출력 프로토콜 - 에이전트 간 API 계약

다른 에이전트가 **이 에이전트의 산출물을 읽을 경로와 형식**을 정함.
FE가 BE API의 응답 형식을 알아야 하듯, 다음 에이전트는 이전 에이전트의 출력 위치와 형식을 알아야 함.

- 나쁜 예 ; 입출력 섹션이 아예 없는 경우 -> 에이전트는 결과를 매번 즉흥적으로 결정함

```md
## 입력/출력 프로토콜

1. 세계관 설계
2. ...
```

- 좋은 예(worldbuilder)

```md
## 입력/출력 프로토콜

- 입력: 사용자의 세계관 컨셉, 장르 요구사항
- 출력: `_workspace/01_worldbuilder_setting.md`
- 형식: 마크다운. 섹션별 (물리/사회/기술/역사/장소)
```

경로를 명시하면 세 가지가 따라와. 다른 에이전트가 Read로 가져올 수 있고, 01\_번호가 파이프라인 순서를 드러내며, 오케스트레이터가 수집 경루를 예측할 수도.

팀이 커질수록 암묵적 계약은 깨지고 파일에 적힌 계약만 살아남아.

#### 4. 팀 통신 프로토콜 - 누구에게, 무엇을, 언제

SendMessage 도구로 주고받을 정보의 세 요소; 누구에게/무엇을/언제 를 명시함.
오케스트레이터가 TeamCreate로 팀을 구성하는 팀 모드에서만 의미가 있음. 단독으로 호출되는 서브에이전트라면 이 섹션은 생략해도 돼.

- 나쁜 예

```md
## 팀 통신 프로토콜

- 필요하다면 다른 에이전트에게 메시지를 보낸다.
```

- 좋은 예(worldbuilder)

```md
## 팀 통신 프로토콜

- character-design에게: 사회 구조, 계급 시스템, 직업군 정보 SendMessage
- plot-architect에게: 세계의 주요 갈등 구조, 위기 요소 SendMessage
- science-consultant로부터: 과학적 오류 피드백 수신 -> 설정 수정
- 세계관 변경 시 관련 팀원 전체에 브로드캐스트
```

메시지를 작성할 때 기억할 원칙 하나:

- 좋은 메시지 = 발견 사실 + 수신자가 취해야 할 행동

-> "완료했습니다" 보다, "~ 반영해 주세요" 로 끝나야 수신자가 다음 액션을 뭘 할지 분명해지고 브로드캐스트 비용을 효율적으로 쓸 수 있어.

#### 5. 에러 핸들링 - 종료 조건 명시

구체적인 실패 시나리오, 각 시나리오에서의 행동, 최대 재시도 횟수를 정해둠. 이게 빠지면 에이전트는 예상치 못한 상황에서 무한 대기하거나, 잘못된 결과를 조용히 넘기거나, 팀 전체를 멈춰 버림.

- 나쁜 예

```md
## 에러 핸들링

- 실패 시 재시도한다.
```

- 좋은 예(webtoon-reviewer)

```md
## 에러 핸들링

- 이미지 로드 실패 시 해당 패널을 REDO로 판정
- 2회 재생성 후에도 REDO인 패널은 경고와 함께 PASS 처리
```

#### 6. 협업 - 팀 안에서의 위치 결정

이 에이전트가 **누구와 어떤 순서로 연결되는지 명시**함. 단독으로 호출되는 서브에이전트라면 생략해도 돼.

```md
## 협업

- 상류: commit-message 스킬이 이 에이전트를 호출한다.
- 하류: commit-msg-reviewer가 이 에이전트의 draft를 읽는다.
- 재호출: reviewer 판정이 FIX/REDO일 때 스킬이 최대 2회까지 재호출한다.
```

#### 7. 품질 자체 검증 - 제출 전 자기 점검

출력을 반환하기 전에 **에이전트가 스스로 거쳐야 할 체크리스트**.

- 좋은 예(chapter-writer)

```md
## 품질 자체 검증 (제출 전)

- [ ] 메타데이터 주석 포함
- [ ] 분량 2,500 ~ 4,000 단어 범위
- [ ] Part별 포맷 필수 섹션 모두 포함
- [ ] 모든 수치·인용에 출처 표기
- [ ] 용어 사전과 충돌 없음
- [ ] 코드 블록 컴파일/실행 가능 (의사코드면 명시)
- [ ] 크로스 레퍼런스가 실제 존재하는 장 가리킴
```

### 가드레일 - 에이전트가 할 수 없는 것을 파일로 정하기

'품질 자체 검증'이 에이전트가 스스로 점검하는 층이라면, 그 바깥에 한 층이 더 있음. 에이전트가 아예 실행할 수 없도록 파일 자체에서 막아두는 층인데 프론트매터의 tools 가 그 역할을 해. 명심해야 할 것은 **자연어 지시는 안전장치가 아니라는 것**

본문에 마크다운으로 금지사항을 써두는 건 프롬프트일 뿐, 에이전트의 행동을 원천적으로 막지는 못함.

tools 필드는 이 가드레일 역할을 하는 1순위 도구로써, 아래 세 가지 방식으로 적용함

- 최소 권한
  - 운영체제의 권한 관리(RBAC)를 AI에게 적용한 것
  - 예를 들어 Read·Grep만 주고 Write·Edit 빼두면 프롬프트를 잘못 해석해도 본문을 직접 수정할 수 없어
- 도구 최소화
  - Vercel의 실험에서 에이전트 도구를 15개에서 2개로 줄였더니 정확도가 80%에서 100%로 올라감
  - 선택지가 너무 많으면 오히려 판단이 흐려지는 '토큰 마비' 발생
- 명시적 제외
  - 상속된 도구 집합에서 특정 도구만 빼고 싶다면 `disallowedTools` 사용. 적용 순서가 선순위야.

### 프론트매터 다섯 필드와 16개 공식 필드

7개 섹션이 본문의 뼈대라면, 프론트매터는 호출자에게 보이는 명함.
클로드 공식 문서 기준으로 프론트매터 필드는 16개가 있지만 실제로 매일 쓴는 건 보통 5개(name, description, model, tools, disallowedTools)

- name, description 은 필수 필드
- 각 필드에 대해서는 78p 표 참고

책의 여러 예제와 후술할 7개 에이전트 팀의 파일에는 `type: general-purpose`라는 키가 자주 보이는데 이는 공식 스펙 16개에 없는, 파서가 읽지 않는 문서화용 키.

#### name·description - 언제 호출될지 결정

**name은 파일명과 반드시 일치시켜야 함.** description은 오케스트레이터가 '이 에이전트를 언제 쓸지' 판단하는 근거

- 나쁜 예

```md
description: "세계관을 만드는 에이전트"
```

- 좋은 예

```md
description: "SF 소설의 세계관을 구축하는 전문가. 물리 법칙, 사회 구조, 기술 수준, 역사를 설계한다."
```

description은 이름표가 아니라 호출 트리거라 봐도 무방해서, 모호하게 쓰면 오케스트레이터가 엉뚱한 에이전트를 부르거나 아무도 부르지 않는 상황이 생김

#### model - 추론 깊이에 따른 결정

model 필드는 비용·모델 등급·응답 속도를 한꺼번에 결정.
기본값은 inherit.

결정 기준은 요구되는 추론 깊이.

- Haiku : 읽기 전용 탐색, 파일 검색처럼 단순한 작업. 클로드 코드의 Explore 서브에이전트가 Haiky를 쓰는 이유도 빠른 응답 속도임.
  코드 grep, 디렉터리 탐색, 간단한 요약에 적합
- Sonnet : 코드 리뷰, 패턴 분석, 중간 길이 생성, 공식 문서 Quickstart도 코드 패턴 분석에 Sonnet을 권고함
- Opus: 다단계 추론, 장문 생성, 아키텍처 설계, 교차 검증. 여러 기준을 동시에 따져 판정을 내려야 하거나 장문의 일관성이 중요할 때 선택함

#### tools - 부작용 범위에 따라 결정

tools는 에이전트에게 허용할 도구 목록. 생략하면 부모 컨텍스트의 모든 도구가 상속돼. 이 필드의 결정 기준은 **에이전트가 일으킬 수 있는 부작용의 범위**임

도구를 너무 많이 주면 역할과 무관한 도구 설명이 시스템 프롬프트에 들어가 토큰을 낭비하고, 에이전트가 본래 영역 밖으로 나갈 가능 성이 커짐.
너무 적게 주면 작업이 조용히 실패함

disallowedTools와 함께 쓸 때는 tools 보다 먼저 적용되어, 상속 목록에서 해당 도구를 제거하고 남은 집합에 tools 필터가 적용됨.

#### 저장 위치와 우선순위

에이전트 파일은 아래와 같이 다섯 곳에 둘 수 있고, 이름이 같으면 상위가 우선함

1. Managed settings -> 조직 전역
2. --agents CLI flags -> 현재 세션
3. .claude/agents/ -> 프로젝트
4. ~/.claude/agents -> 사용자 전역
5. 플러그인 agents/ -> 플러그인 활성화 시

#### 핵심 파일 읽기 - copy-editor.md

추후 추가될 `copy-editor.md` 파일을 확인ㅁ하거나 책 내용 82p~88p 참고

### 안티패턴

1. 무엇이든 다하는 에이전트
   - 결과적으로 전문성이 없는 영역에도 답을 내놓고, 단일 에이전트가 자기 실수를 잘 보지 못하는 문제가 그대로 재현돼
   - 역할을 잘게 쪼개는 걸로 어느 정도 해소가 되지만 그렇다고 너무 잘게 나누는 것도 주의 해야
   - 분리와 통합을 판단하는 기준으로 "전문성", "병렬성", "컨텍스트", "재사용성" 4가지 참고

2. 도구를 너무 많이 줬을 때
   - tools를 생략하거나 전부 열어두면
     - 토큰이 불필요하게 늘어나고 실행 경로가 많아지며
     - 검토 역할 에이전트에 Edit 권한이 남아 있으면 검토 에이전트가 직접 수정까지하면서 검증 루프가 무너져

3. model 필드를 비워두는 경우
   - 기본값 inherit일 때는 부모 세션에 따라 에이전트의 동작이 달라져
   - 이는 재현성이 깨지고 디버깅도 어려워져
   - 상속을 의도했다면 model: inherit으로 명확히 적어

4. description이 너무 막연할 때
   - 무엇을 / 어떤 기준으로 / 언제 호출하는지 이 세 가지를 한 줄에 담아

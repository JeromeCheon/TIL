# 스킬 설계의 기술

## 학습 목표

스킬 본문을 아무리 잘 작성해도 description을 통과 못해 열리지 않고 에이전트가 사용하지 않는 경우가 다반사.
description을 Pushy 3단계(동사 나열·트리거 상황·경계 조건)로 작성하는 방법과 Progressive Disclosure 구조 이해.
규칙이 아닌 이유를 본문에 담는 Why-First 원칙을 실제 예시로 확인

## 핵심 키워드

- description
- Pushy 3단계 공식
- Progressive Disclosure
- Why-First 원칙
- 트리거 매칭

### 스킬을 썼는데 왜 호출이 안 될까

클로드의 스킬 호출은 본문이 아니라 한 줄의 description 이 결정함.
description이 모호하면 아무리 잘 만든 본문도 영영 읽히지 않아.

스킬 호출 방법에는 사용자가 /skill-name 으로 직접 호출하거나 프론트매터에 paths: [] 같은 경로 기반 트리거를 설정하는 것도 있음.

이 장에서는 이 두 방식이 아니라, 클로드가 사용자의 자연어 요청을 보고 스스로 스킬을 고르는 것에 대해 다룸.

자동 호출에는 공간 제약도 있는데, 세션이 열릴 때 전체 컨텍스트 윈도우의 약 1%만 스킬 목록에 씀.
스킬이 30개면 하나당 쓸 수 있는 글자 수가 얼마 안되기에, description을 짧으면서 구체적으로 작성하는 기술을 다룰 것

#### 이 장에서 다루는 세 가지 원리

1. Pushy 3단계 공식

- "왜 호출되어야 하는가"가 드러나도록 쓰는 방법

2. Progressive Disclosure(단계적 정보 공개)

- 전체 스킬을 세 층으로 나눠, 꼭 필요한 것만 먼저 보여 주고 나머지는 필요할 때만 불러오는 방식.

3. Why-First 원칙.

- 본문에 규칙 대신 이유를 싣는 방법

### 원리 1 - Description이 호출을 결정한다

클로드는 자체 기능으로 충분히 처리할 수 있다고 판단한 요청에는 스킬을 호출하지 않는 경향 있음.

보수적인 클로드를 움직이게 하기 위해 description 작성 전략도 바꿔줄 필요가 있어.

#### 효과적인 description 작성 공식

1. 동사 나열
   - 스킬이 실제로 수행하는 동작을 동사로 적음
   - ex. 읽기, 추출, 병합, 분할, 회전, 워터마크 삽입, 암복호화, OCR 처리" 처럼
2. 트리거 상황
   - "사용자가 ~을 언급하면 이 스킬을 사용할 것"처럼 직접적인 조건문을 넣음
   - 배포 스킬 ex. deploy, 배포, 릴리스, release 처럼 한국어와 영어 표현 함께
3. 경계 조건
   - 본 스킬이 적합한 경우뿐 아니라 적합하지 않은 경우도 함께

### 원리 2 - Progressive Disclosure 3단계

#### 컨텍스트는 공공재다

컨택스트 윈도를 작업 책상으로 보았을 때 책상 위에 놓는 서류 양은 한정되어 있어, "지금 필요한 것만 책상 위에 올려둔다"는 원칙이 필요함.
일종의 lazy loading 과 같이.

여기서 감안해야 할 것이, 컨텍스트는 내 것이 아니라 공공재라는 것.

#### 3 단계 구조

- Layer 1 : "이 스킬을 호출할 것인가"
- Layer 2 : "호출했다면 어떻게 수행하는가"
- Layer 3 : "특정 조건에서 무엇을 추가로 참고하는가."

#### 언제 본문을 쪼갤 것인가 - 분리 신호 세 가지

본문을 references로 분리할 타이밍을 판단하는 기준은 세 가지.

- 크기 신호 : SKILL.md가 500줄에 근접
- 도메인 분기 신호 : "매출이면 A, 재고면 B"
- 조건부 상세 신호 : "추적 변경이 필요하면 REDLINNING.md 참조" 같은 조건부 링크 쓰고 싶을 때

### 원리 3 - Why-First 원칙

명령형 규칙만 쓰면 LLM 대상으로는 역효과를 낼 수 있음. 반면, 명시된 이유를 알면 새로운 상황에서도 스스로 판단할 수 있는 기회를 줘.

인간용 매뉴얼은 자의적인 판단을 배제하기 위해 규칙을 쓰지만, LLM용 지시서는 반대로 엣지 케이스에서도 생각을 이어갈 수 있도록 이유를 심음.

#### 일반화 vs 오버피팅

조금이라도 넓게 적용될 수 있게 규칙을 일반화해야 재사용 가치가 올라가

Why-First가 **규칙에 이유를 붙이는 것**이라면, 일반화는 **규칙의 적용 범위를 넓히는 것**

#### 컨텍스트 절약 3원칙

1. 클로드가 이미 아는 내용인가: 파이썬 문법, 기본 HTTP 상태 코드
2. 이 설명이 없으면 클로드가 실수 하는가: 프로젝트 관례, 특성, 비표준 명명 등 클로드가 알 수 없는 맥락은 남겨둔다
3. 구체적 예시 하나가 긴 설명보다 효과적인가: 그렇다면 예시로 대체

어조 역시 경어체보다 명령형을 쓰는게 더 명료해.

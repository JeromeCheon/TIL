# 오케스트레이터

이 장에서는 팀원들이 리더를 거치지 않고 서로 직접 대화할 수 있게 해주는 세 가지 도구, TeamCreate·TaskCreate·SendMessage를 다룸

## 학습 목표

리더 중심 통신이 왜 팀 성능을 떨어뜨리는지 이해하고, 클로드 코드에서 제공하는 기본 도구를 각각 언제 어떻게 쓰는지 파악함.
리더가 폴링 없이 팀을 조율하는 이벤트 루프 구조를 이해하고, 에이전트 정의 파일에 팀 통신 프로토콜을 올바르게 작성하는 방법 익힘

## 핵심 키워드

- TeamCreate
- TaskCreate
- SendMessage
- 팬아웃·팬인
- 리더 병목

### 3인이 넘으면 리더가 무너진다

PR 리뷰를 하는 가정 하에, `security-reviewer`는 OWASP 관점에서 취약점을, `perfomance-reviewer`는 N+1 쿼리와 병목을, `test-reviewer`는 변경 범위 대비 커버리지를 보고 리더는 PR 링크를 받고 이 셋을 호출함.

리뷰 도중 이슈가 발견되어 각 에이전트가 메시지를 보내고 리더가 이를 수렴해서 연관 에이전트에게 다시 보내는 구조면,
병렬로 시작한 리뷰가 병목에서 다시 순차 파이프라인으로 퇴행함.

> "리더는 우체국이 되었고, 팀원들은 서로 모르는 채로 각자의 방에 갇혀 있습니다. official-researcher가 흥미로운 경쟁사 발표를 발견해도, background-researcher는 리더가 중개해줄 때까지 그 사실을 모릅니다." <br><br>-클로드 오케스트레이션 공식 가이드

### 리더는 이벤트 루프, 팀원은 피어

- 잘못 설계된 오케스트레이터: 모든 소통의 중심에 리더가 있어야 함
- 잘 설계된 오케스트레이터: 리더는 중앙 중개자가 아닌, **수신자이자 통합자**의 위치. 핵심은 _병렬성_ !!

이벤트가 들어왔을 때만 반응하는 것.

### 세 가지 기본 도구 - 팀을 데이터 전달 방식으로 보기

데이터를 주고받는 방식에 따라 크게 세 가지로 나눌 수 있음.

- 팀을 구성하는 도구
- 할 일을 만들고 추적하는 도구
- 팀원들이 서로 메시지를 주고 받는 도구
  \+ 여기에 실무에서는 _파일 기반 전달 규약_ 까지.

### TeamCreate - 팀은 상수가 아니라 세션 객체

팀은 파일에 영구적으로 정의되지 않고, 세션이 시작될 때 리더가 호출해 메모리 위에 만들고 세션이 끝나면 사라지는 구조.

실제 클로드 코드 구현에서 팀 구성은 두 단계로 나뉨.
먼저 TeamCreate로 팀 껍데기를 만들고 각 팀원은 AgentTool을 team_name 필드와 함께 호출해 개별적으로 생성함

[orchestrator-template.md](https://github.com/revfactory/harness/blob/main/skills/harness/references/orchestrator-template.md) 와 책 113p 를 참고하여 구조를 짚고 넘어가자.

주요 사항을 정리하면 다음과 같음

- `AgentTool`의 `name`:
  - 팀 내부 주소
  - 같은 팀 안에서 SendMessage({to: "security-reviewer"}) 형태로 이 이름이 목적지가 돼.
- `model`(생략 가능):
  - 팀원별로 다르게 잡을 수 있음 (감독자는 opus, 단순 추출자는 haiku 이런 식)
  - 명시하지 않으면 부모 세션의 모델을 상속
- `prompt`:
  - 런타임 작업 지시
  - 에이전트 정의 파일의 본문과 합쳐져서 실제 system prompt가 구성됨
  - 여기서 중요한 건 에이전트 파일에 정의된 역할과 호출 시점의 작업 컨텍스트가 분리된다는 점!
- `isolation`:
  - "worktree" 파일 격리 옵션
  - 팀원이 서로의 작업 중인 파일을 덮어쓰지 않도록 git worktree로 격리
  - 클로드 코드 공식 템플릿이 이 필드를 명시적으로 채택함

### TaskCreate / TaskUpdate - 공유 작업 큐와 depends_on

할 일을 왜 SendMessage만으로 다 처리하지 않을까?
이는 단순한 텍스트가 아니라 세가지 속성을 동시에 갖기 때문.

- 소유자(누가 하는가)
- 상태(시작했나, 끝났나)
- 의존성(무엇이 먼저 끝나야 하나)

이를 메시지로만 관리하려면 팀원마다 같은 장부를 복사본으로 들고 있어야 하고, 이게 어긋나는 순간 팀은 막힘.
TaskCreate 는 이 장부를 팀 모두가 공유하는 단일 소스로 제공함

클로드 코드에서 이걸 호출할 때 아래 네 가지 특성이 녹아져 있음.

1. 동시 시작 가능한 작업은 동시에 시작돼
   - ex. '보안 리뷰', '성능 리뷰'는 서로 의존성이 없으므로 두 팀원이 병렬로 착수
2. depends_on이 있는 작업은 전제 작업이 끝날 때까지 대기.
   - 리더가 수동으로 순서를 제어하지 않아도 돼
3. 팀원은 장부를 직접 읽고 씀
   - TaskList로 큐를 읽고, TaskUpdate로 자기 작업을 가져가겠다고 선점(claim)하고 완료를 보고.
   - 장부는 파일 기반이지만 동시성이 보장돼
4. 리더는 TaskGet으로 전체 진행률을 확인함
   - 어느 작업이 대기중이고, 누가 무엇을 들고 있고, 뭐가 완료됐는지 등 모니터링

### SendMessage - 리더를 거치지 않는 peer-to-peer 채널

기본 도구들 중에 가장 <u>극적인 도구</u>는 `SendMessage`야.
리더의 병목을 실제로 깨기 때문.

구성 요소로는, to, summary, message가 있음.

- to
  - 같은 팀의 팀원 이름
- summary
  - 수신자에게 표시되는 한 줄 요약
- message
  - 본문. 리더를 거치지 않고 발신자의 출력에서 수신자 입력으로 바로 전달.

### 리더의 역할

기본 도구를 엮으면 리더의 할 일이 분명해짐.
지시가 아닌 _통합, 유휴 알림 처리, 에러개입 등_.

### 실전 예제 - PR 리뷰 오케스트레이터 SKILL.md

120p ~122p 참고.
이 예제에서의 핵심은 오케스트레이터가 '리뷰를 잘하는 프롬프트'가 아니라는 것.

리뷰는 네 팀원이 하는데 오케스트레이터는 팀이 언제 생기고, 어떤 작업이 병렬로 돌고, 어떤 조건에서 멈추는지 등을 정함.

이 파일 하나가 6장의 세 기본 도구를 실제 운영 규칙으로 묶은 최소 단위라고 할 수 있음.

#### 292개 에이전트 사건

그렇다면 이제 "팀을 얼마나 크게 만들어도 되는가"를 고민해야 할 차례.

SendMessage가 full mesh 를 허용하는 만큼, 이 경로 수가 곧 팀원이 신경 써야 하는 잠재적 대화 상대의 수.
4명일 때 6개는 감당 가능하지만, 10명이 되면 45개가 되고 각각에 대해 적절히 반응하려면 자기 컨텍스트 윈도의 상당 부분을 메시지에 빼앗김.

즉, 실제 작업에 쓸 컨텍스트가 줄어듦.

클로드 코드가 팀원 메시지 큐를 50개로 제한한 이유가 여기 있음.
팀을 너무 크게 만들면 메모리가 한계에 도달하고, 메시지 큐가 무관한 컨텍스트로 가득 차며, 오히려 품질이 떨어짐

### TeamDelete와 정리 - 세션당 한 팀, shutdown 필수

팀을 만드는 것만큼이나 정리도 설계의 일부.
클로드 코드는 세션당 활성 팀을 하나로 제한함.

### 언제 팀 프리미티브를 도입할까

2인, 생성-검증 구도, 실시간 피드백 불필요라는 세 조건에서는 프리미티브가 오히려 과한 설계(오버엔지니어링)가 돼.

'팀이냐 서브에이전트냐'의 상세 선택 기준과 하이브리드 설계는 9장에서 다룰 것.

여섯 가지 아키텍처 패턴(파이프라인, 팬아웃 팬인, 전문가 풀, 생성-검증, 감독자, 계층적 위임)의 분류도 8장에서 다룰 것.

### 관측과 경계면 - 팀을 바깥에서 보기

팀이 세 프리미티브 위에서 자율적으로 움직이기 시작하면 리더에게는 새로운 차원의 책임이 더해짐.

"팀을 바깥에서 지켜보는 일"

이 때 오케스트레이터는 **관측**과 **경계면** 두 가지를 책임져야 함.

#### 관측 - 반복 수준 로깅

전통 소프트웨어의 3기둥(로그,메트릭,트레이스)은 여기서도 유효하지만 담기는 내용이 달라.

오케스트레이터의 관측 역할은 크게 둘.

1. 각 팀원의 훅이 남긴 로그를 중앙 한 곳에 모음
2. 임계치를 넘어설 때 개입함

#### 경계면 - 팀원 둘이 각자는 맞지만 합이 틀릴 때

관측이 팀을 시간축에서 본다면, 경계면을 고려하는 것은 팀을 공간축에서 보는 것.

오케스트레이터의 설계 책임은 이 경계면을 명확히 하는 일.

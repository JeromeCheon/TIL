# 메타 하네스 스킬과 6단계 파이프라인

팀을 몇 번 만들다 보면 반복되는 반복되는 패턴이 있을 것. 어차피 반복할 거라면 그 과정 자체를 스킬로 만든다면?

메타스킬은 스킬과 에이전트를 만드는 스킬임

## 학습 목표

- 메타 스킬이 일반 스킬과 어떻게 다른지 이해
- harness SKILL.md 실제 파일 구조를 통해 Progressive Disclosure와 자기 참조성이 어떻게 구현되는지 확인
- 6단계 파이프라인의 각 Phase에서 무엇을 실행하고 무엇이 산출되는지 파악
- 하네스가 한 번 만들면 끝이 아니라 계속 순환하며 발전하는 이유를 이해

## 핵심 키워드

- 메타스킬
- harness SKILL.md
- 6단계 파이프라인
- 자기 참조성
- 하네스 자동화

## 줄거리 요약 및 정리

### 여섯 번째 팀을 만들던 날

2부 요약: 에이전트 정의, 스킬 설계, 오케스트레이터로 팀을 움직이고, 가드레일&검증을 훅으로 꽂고, 접두사와 계층을 맞춰 비용을 잡음

근데 이 엔지니어링을 매번 똑같이 반복해야 하나?

-> 이 역시 스킬의 재료로 보고 스킬로써 설계 가능한 것 아닌가?

"어떤 작업을 어떻게 수행하는가" 같은 보통의 스킬이 아니라, "어떤 스킬과 에이전트를 만들어야 하는가"를 담는 상위 차원의 스킬

### 메타스킬이란 무엇인가

meta-skill : 스킬과 에이전트를 만드는 스킬

이 스킬의 결과물은 새로운 **에이전트 파일**과 **스킬 파일**

#### 실전 파일 - harness SKILL.md

```md
**핵심 원칙:**

1. 에이전트 정의(`.claude/agents`)와 스킬(`.claude/skills/`)을 생성한다.
2. **에이전트 팀을 기본 실행 모드로 사용한다.**
3. **CLAUDE.md에 하네스 포인터를 등록한다.**
4. **하네스는 고정물이 아니라 진화하는 시스템이다.**
```

2부에서는 위 4가지를 직접 구현했다 라고 하면 메타스킬은 이 네 가지를 **규약으로 강제**함.

특히 4번 원칙(항목) "진화하는 시스템"은 3부의 주요 핵심이 순환하는 루프로 서술된다는 것을 예고함.

[SKILL.md](harness-engineering-with-claude/part3/.claude/skills/harness/SKILL.md)의 본문은 총 443 라인으로, 2부에서 정한 현실적 최대치인 500줄을 넘지 않으면서 상세 내용을 references/ 아래 6개 파일로 나눠서 필요시 참조하도록 썼어.

이 구조를 통해 알 수 있듯, 메타스킬은 자신이 정의한 규칙을 자기가 따르는 **자기 참조성** 성격을 가짐.
개발자 관점에서 자기 참조성이 주는 실용적 가치는 검증 가능성임

메타스킬이 하는 일은 '잘 설계된 팀을 빠르게 만드는' 것이지, 아무 팀이나 만드는 일이 아님.

### 메타스킬이 여는 6단계 파이프라인

하네스를 구성한다는 것은 즉흥적인 작업이 아니라, **도메인 분석 -> 팀 설계 -> 정의 -> 스킬 -> 오케스트레이션 -> 검증**의 여섯 관문을 통과하는 일.

### Phase 1. 도메인 분석 - 질문을 정제하는 단계

이 단계는 답을 만드는 단계가 아니라, 질문을 정제하는 단계.
정제할 항목은 아래 다섯 가지.

1. 도메인과 핵심 작업 유형
   - 데이터 분석 파이프라인인가, 콘텐츠 생성인가, 웹 앱 개발인가 등 유형이 다르면 이후 팀 구조가 달라짐
2. 기존 에이전트와 스킬의 현황
   - .claude 내 파일들 먼저 읽음
   - 빈 프로젝트가 아니라면 이미 있는 구성과 새 구성이 충돌할 수 있음
3. 프로젝트 코드베이스 탐색
   - 기술 스택·데이터 모델·모듈 경계를 파악함
   - 이 경계선은 phase 3에서 에이전트를 분리할 때의 기준선이 돼
4. 사용자 숙련도 감지
   - 쓰는 용어와 질문 수준으로 기술 배경을 파악함
   - 같은 요구라도 요구하는 답변 층위가 다름
5. 기존 에이전트와의 충돌·중복
   - Phase 1에서 발견해야 함. phase 3에서 발견하면 이미 늦음

이 phase 1에서의 산출물은 **'분석 메모'**임.

### Phase 2. 팀 아키텍처 설계

이 단계에서의 첫 질문은 단순해: "작업들이 서로 기다려야 하는가, 동시에 할 수 있는가?"
기다려야 하면 파이프라인, 동시에 할 수 있으면 팬아웃이 기본 후보. 이렇게 시작해서 구체적인 패턴으로 좁혀가.

Phase 2에서 내릴 결정은 두 가지.

1. 실행 모드
   - 에이전트 팀(TeamCreate 기반 다중 에이전트)인가, 서브에이전트(단일 Agent 직접 호출)인가, 하이브리드 인가
   - 기본은 에이전트 팀이지만, 단일 작업·결과 반환만 필요한 경우 서브에이전트가 더 가벼움
   - 단계마다 특성이 다르면 phase 단위로 팀/서브를 섞는 하이브리드가 답일 수도.
2. 아키텍처 패턴
   - 에이전트 팀 선택 했다면 아래 여섯 가지 패턴 중 하나를 고름
     - 파이프라인, 팬아웃/팬인, 전문가 풀, 생성-검증, 감독자, 계층적 위임
     - 자세한 내용은 p140 참고

이 단계에서 내린 결정은 나중에 되돌리기가 까다롭기 때문에 제대로 결정해야 함.

여기서의 산출 결과물은 '팀 설계도'임. 에이전트 이름 목록과 그들 사이의 통신 방향을 반드시 명시함.

### Phase 3·4. 에이전트와 스킬 - 파일이 없으면 존재하지 않는다

3,4 단계는 2 단계의 설계도를 실제 파일로 만드는 단계.
Phase 3이 **누가 일하는가**(에이전트)를, Phase 4가 **어떻게 일하는가**(스킬)를 담당함

#### Phase 3 에이전트 정의의 핵심

모든 에이전트는 반드시 `.claude/agents/{name}.md` 파일로 정의함

여기서 실제로 결정해야 하는 것은 내부 구조가 아니라 **에이전트를 어디서 자를 것인가**임

#### Phase 4 스킬 생성의 핵심

에이전트가 매번 같은 절차를 반복해야 한다면 그 절차를 스킬로써 분리!

스킬의 핵심 개념은 **단계적 정보 공개**(Progressive Disclosure)

### Phase 5. 오케스트레이션

지금까지 만든 에이전트와 스킬을 실제 워크플로로 묶음. 이 단계의 핵심은 "리더는 모니터이지, 중계자가 아니다" 라는 것

데이터 전달은 아래 세 가지 방식의 조합임

- 조율
- 최종 산출물
- 실시간 소통

phase 5는 이 프리미티브들을 오케스트레이터 스킬 하나로 묶는 단계.

### Phase 6. 검증

**측정 가능한 비교**로 잘 만들어졌는지 판단.

같은 테스트 프롬프트를 두 에이전트(With/Without)에 던져보고 두 결과를 나란히 놓고 비교.

스킬 없이도 같은 결과가 나온다면, 그 스킬은 불필요함. 스킬이 있다는 사실만으로 품질이 올랐다고 추정하면 단순한 확증 편향에 빠지기 쉬움.

실제 SKILL.md는 Phase 6를 여섯 서브 단계로 쪼갬

- 6-1. 구조 검증: 파일 위치, 프론트매터, 참조 일관성 확인
- 6-2. 실행 모드별 검증: 팀, 서브에이전트, 하이브리드별 체크
- 6-3. 스킬 실행 테스트: With vs Without
- 6-4. 트리거 검증: should-trigger + should-NOT-trigger
- 6-5. 드라이런 테스트: Phase 순서 검증. 끊어진 링크 탐지
- 6-6. 테스트 시나리오 작성: 정상 시나리오 1개 + 에러 시나리오 1개 이상

Phase 6의 산출물은 테스트 리포트임.
리포트에 실패가 있으면 Phase 3~5로 돌아가 수정한뒤 다시 6 돌림.

### Phase 0·7 순환 구조와 메타 하네스 루프

6단계까지 완주했다고 파이프라인이 끝나는 것은 아님.
첫 행동으로 '읽기'를 선언하고, 단계들을 거쳐서 Phase 7에서는 실행하고 얻은 피드백을 바탕으로 결과물 품질 문제 -> 스킬, 역할 혼동 -> 에이전트 파일, 순서 문제 -> 오케스트레이터로 각각 반영.

> 하네스는 한번 만들고 끝나는 산출물이 아니라 계속 관리하는 대상

### 안전장치 - 메타스킬도 폭주할 수 있다

메타스킬은 무제한이 아니며 깊이는 설계로, 누적은 운영으로 통제한다는 것을 명심하자.

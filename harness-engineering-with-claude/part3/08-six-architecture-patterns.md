# 여섯 가지 아키텍처 패턴

팀 구조를 잘못 고르면 좋은 에이전트도 힘을 못 씀.
이 장에서는 실무에서 자주 쓰이는 여섯 가지 패턴의 특징과 선택 기준을 정리함.
패턴을 먼저 골라 끼워 맞추는 게 아닌, 문제의 구조를 보면 패턴이 자연스레 결정됨.

## 학습 목표

에이전트 분리 결정 네 가지 기준 익히고, 여섯 가지 패턴 각각의 특징과 적합한 상황을 파악.
나아가 실전에서 훨씬 흔한 복합 패턴을 어떻게 조합하는지도 살펴봄.

## 핵심 키워드

- 파이프라인
- 전문가 풀
- 감독자 패턴
- 팬아웃, 팬인
- 생성 검증
- 계층적 위임
- 복합 패턴

## 줄거리 및 요약

### 팀에는 모양이 있다.

6장에서 프리미티브(TeamCreate, TaskCreate, SendMessage)를 손에 쥐었고, 7장에서 6단계 파이프라인으로 팀을 설계하는 절차를 익혔음.

그렇다면 남은 질문은 "팀의 모양을 어떻게 고를 것인가?"

모양을 잘못 고르면 기본 프리미티브 도구들이 제 역할을 하지 못해. 구조적 아키텍처가 다르면 그 결과는 완전히 달라진다.

실무에서 굳어진 아키텍처 패턴은 6가지이다.

> 파이프라인, 팬아웃·팬인, 전문가 풀, 생성-검증, 감독자, 계층적 위임

결정에 앞서 세 가지 원칙을 정리하자면 다음과 같다.

1. 문제의 구조를 정확히 파악하면 패턴은 자연스럽게 따라옴.
   - 패턴을 먼저 고르고 문제를 끼워 맞추면 안돼
2. 단일 패턴보다 복합 패턴이 실전에서 훨씬 흔해.
   - Phase 마다 다른 패턴을 쓰고, Phase 간 경계는 \_workspace/ 파일로 이음
3. 계층은 2단계 이내로 유지함
   - 3단계부터 지연과 컨텍스트 손실이 기하급수적으로 커짐

### 에이전트를 몇 명으로 쪼갤 것인가

패턴은 에이전트 수를 전제로 하기에, 분해 기준이 먼저 필요함

| 기준     | 분리 이유                        | 통합 이유            |
| -------- | -------------------------------- | -------------------- |
| 전문성   | 역할 영역이 명확히 다름          | 역할 영역이 겹침     |
| 병렬성   | 독립적으로 실행 가능             | 순차 의존이 강함     |
| 컨텍스트 | 처리 부담이 크고 무거움          | 가볍고 빠른 작업     |
| 재사용성 | 다른 팀·프로젝트에서 재활용 가능 | 이 팀에서만 의미있음 |

위 기준들 중 '분리해야 할 이유'가 두 가지 이상이면 별도 에이전트로 분리하는게 좋고, 세 가지 이상 모두 '통합 이유'가 더 타당하다 싶으면 한 에이전트 안에 두는게 나음

### 패턴 1. 파이프라인 - 순서가 의미를 만든다

이전 단계의 출력이 다음 단계의 입력으로 이어지므로, 수행 순서가 바뀌면 전체 논리가 무너짐

> 정적 점검 - 설계 검토 - 보안 점검 - 리팩터링

순서가 잘못된 파이프라인은 거의 항상 재실행 비용이 추가됨.

아래 이유가 있다면 이 패턴을 선택하면 좋다.

- 앞 결과 없이는 뒷 에이전트가 시작할 수 없는 강한 순서 의존이 있을 떄
- 단계별 역할 경계가 명확해서 책임을 넘기기 쉬울 때
- 중간 산출물이 코드·문서·다이어그램처럼 확인 가능한 형태로 나올 때

### 패턴 2. 팬아웃·팬인 - 같은 입력, 다른 관점

같은 입력을 여러 에이전트가 동시에 본 뒤, 리더가 결과를 통합함

PR 리뷰가 가장 대표적인 예시.
이 패턴이 단순 병렬과 다른 결정적인 지점은 **팀원 간 실시간 교차 검증** 이라는 것.

아래 이유가 있다면 이 패턴을 선택하면 좋다.

- 같은 입력을 다른 관점으로 동시에 봐야할 때
- 한 팀원의 발견이 다른 팀원의 방향을 실시간으로 바꿔야 할 때
- 리더가 '무엇을 할지 지시'하기 보다 '결과를 통합'하는 역할에 집중할 때

### 패턴 3. 전문가 풀 - 라우터 + 전문가

입력 유형에 따라 다른 전문가가 호출돼.
팬아웃과 비슷해 보이지만 결정적 차이가 있음

- 팬아웃: N명 모두가 일함
- 전문가 풀: N명 중 한 명만 일함

이 패턴의 핵심은 전문가를 호출시키는 **라우터의 분류 정확도** 인데, 오분류가 발생하면 <u>한 번의 실패로 끝나지 않고, 잘못된 영역에 잘못된 변경을 남겨 돌이킬 수 없는 부작용을 낳음</u>

아래 이유가 있다면 이 패턴을 선택하면 좋다.

- 입력 유형이 몇 가지로 뚜렷이 나뉠 때
- 유형별로 요구되는 전문성이 겹치지 않을 때
- 전문가끼리 실시간으로 소통할 필요가 없을 때

### 패턴 4. 생성-검증 -- 만들고 검사하고 다시 만든다

한 에이전트가 산출물을 만들면, 다른 에이전트가 검증함.
실패하면 재작업함.

이러한 구조로 설계하는 것이 생성-검증.

아래 이유가 있다면 이 패턴을 선택하면 좋다.

- 산출물 품질 보장이 중요할 때
- 검증 기준이 명확할 때(테스트 통과, 린터 경고 0개, 스키마 일치 등)
- 생성과 검증의 관점이 자연스럽게 분리될 때

한편, 생성-검증의 가장 위험한 함정은 **무한 루프** 이므로, 이 상황을 막기 위한 규칙을 반드시 명시해야 함

> ex. 2회 재생성 후에도 REDO면 패널은 경고와 함께 PASS 처리

### 패턴 5. 감독자 - 런타임 동적 분배

감독자가 작업 목록을 관리하고, 워커들이 스스로 다음 작업을 가져가는 방식

팬아웃과 다른 점:

- 팬아웃은 처음에 고정 분배
- 감독자는 진행 상황을 보며 **동적 조정**

감족자의 표준 워크플로는 다음과 같아

| 단계 | 동작                                            | 도구        |
| ---- | ----------------------------------------------- | ----------- |
| 1    | 전체 대상 파일 목록 수집                        | Glob / Read |
| 2    | 복잡도 추정(크기, 의존성)                       | 감독자      |
| 3    | 작업을 큐로 등록(의존성 포함)                   | TaskCreate  |
| 4    | 워커들이 남은 작업을 가져가겠다고 선점(claim)   | TaskUpdate  |
| 5    | 성공 -> 다음 작업 / 실패 -> 원인 확인 및 재할당 | SendMessage |
| 6    | 모든 작업 완료 -> 리더가 통합 테스트            | 감독자      |

이 떄, 4단계 claim이 핵심임. 감독자가 지시하지 않고, 워커가 능동적으로 가져가는 것

아래 이유가 있다면 이 패턴을 선택하면 좋다.

- 작업 수가 실행 전에 정해지지 않고, 실제로 스캔해봐야 알 수 있을 때
- 작업별 처리 시간의 편차가 클 때
- 특정 워커가 막히면 다른 워커가 이어받아야 할 때

### 패턴 6. 계층적 위임 - 총괄 -> 팀장 -> 실무자

문제가 너무 크거나 복잡해서 한 팀이 전부 담당하기 어려울 때, 영역별로 쪼개서 각각의 하위 팀에게 맡기는 구조.

이 패턴에서 가장 주의해야 할 점은 **깊이**!
깊이가 2단계를 절대 넘으면 안돼. 3단계부터는 지연이 기하급수적으로 증가하고, 컨텍스트 손실이 발생함.

아래 이유가 있다면 이 패턴을 선택하면 좋다.

- 문제가 자연스럽게 독립된 하위 영역으로 나뉠 때
- 각 영역이 충분히 복잡해서 실무자 여러 명이 필요할 때
- 2단계로 충분히 커버될 때

### 복합 패턴은 실전의 기본값

단일 패턴 예시는 이해 돕는 목적의 교육용이었다면, 실제 하네스는 Phase 마다 다른 패턴을 쓰고 이 Phase 간 경계를 \_workspace/로 이음.

# 하네스 등록과 진화

CLAUDE.md에 "~에 하네스가 있다" 라는 걸 알려주는게 없다면 스킬 파일이 있어도 새 세션에서 한 번도 호출 안될 수 있음.

이 장에서는 하네스를 처음 불러내는 방법과 계속 살아있게 만드는 방법을 다룸.

## 학습 목표

CLAUDE.md의 4단계 스코프 계층과 4줄 포인터 템플릿 이해하고 작성하는 방법 배움.

또 새 세션에서 하네스가 자동으로 트리거되는 4층 재호출 구조를 파악하고,
하네스가 현실과 어긋나는 드리프트 신호를 어떻게 감지하고 대응하는지 익힘

## 핵심 키워드

- CLAUDE.md
- 하네스 포인터
- 재트리거 시스템
- 드리프트감지
- 4층 재호출 구조
- always-on
- 진화 관리

## 줄거리 요약 및 정리

### 하네스는 진화하는 생명체다

스킬은 "에이전트가 필요할 때 찾아오는" 수동 자원이라서 에이전트가 스스로 "지금 이 스킬을 써야겠다" 판단 안하면 호출 안돼.

또한 등록된 스킬의 결과물이 현실과 어긋나기 시작하는 현상이 생길 수 있다.

이러한 현상은 같은 뿌리에서 나오는데, **하네스가 계속 운영되는 시스템이 아니라 한 번 만든 뒤 멈춰 버린 스냅샷으로 변하고 있다는 것**

핵심 명제는 둘이야.

1. 하네스는 새 세션에서 자동으로 다시 호출되어야(등록) 비로소 운영 시스템이 된다.
2. 하네스는 진화하는 생명체다. 한 번에 하나씩 바꾸고 즉시 기록한다.

등록 없이 진화는 불가능 하기에, 이 장에서는 등록 먼저 다루고 나중에 진화로 넘어가.

### 포인터는 4줄, 시스템은 4층

#### 왜 CLAUDE.md 여야 하는가?

vercel의 벤치마크 결과를 책에서는 인용하면서, AGENTS.md에 명시해두었을 때 성과가 거의 100퍼센트에 수렴함을 보여줌.

클로드 코드의 7개 하네스 계층(CLAUDE.md -> Skills -> Subagents -> Agent Teams -> Hooks -> MCP -> Plugins) 중 CLAUDE.md는 제 0계층이자 유일하게 '항상 활성화' 되어 있는 계층.

#### 4단계 스코프 계층과 하네스 포인터의 위치

CLAUDE.md는 아래 4개의 스코프로 계층화 되어 있음

- 조직 규칙
- 경로 규칙
- 프로젝트 규칙
- 개인 규칙

하네스 포인터의 정식 위치는 **프로젝트 스코프**.
팀 전체가 하네스를 공유하므로 개인 스코프가 아니고, 프로젝트 전반에 적용되기 때문.
이것이 하네스를 공유 가능한 인프라로 만드는 이유이기도 함.

### 하네스 등록 - CLAUDE.md 템플릿과 실전용 변형

#### 정식 템플릿에서의 하네스 포인터

harness skill의 표준 CLAUDE.md 참고.

- 하네스
- 목표
- 트리거
- 변경 이력

'트리거'는 오케스트레이터가 어던 요청에서 스킬을 호출할지 결정함.
포인터는 상세 규칙을 담는 백과사전이 아니라 상세 파일로 연결하는 짧은 안내 격.

#### 담을 것 vs 담지 말 것

하네스 스킬에 명시된 금지 목록과 이유는 다음과 같다.

- 에이전트 목록: .claude/agents 와 중복
- 스킬 목록: .claude/skills와 중복
- 디렉터리 구조: 파일 시스템이 스스로 표현
- 실행 규칙 상세: 오케스트레이터 스킬에 있음

CLAUDE.md는 상세 규칙을 담는 백과사전이 아니라 상세 파일로 연결하는 짧은 안내여야 함.

### 진화의 두 관문 - Phase 0 현황 감사와 7-5 운영 루프

#### 두 가지 drift

drift: 시간이 지나면서 원래 목표나 기록에서 어긋나는 현상

- 에이전트 drift : 에이전트 실행 중 도구 계속 호출하면서 품질이 떨어지는 것
- 구조 drift: 파일 시스템의 에이전트/스킬 현실과 CLAUDE.md의 기록이 달라지는 것

위 두 drift는 서로를 악화시킴.

#### Phase 0 - 모든 스킬 실행의 첫 관문

harness skill은 모두 이 0단계부터 시작함.
즉 트리거가 잡히면 먼저 기존 하네스 현황을 확인하고 실행 모드를 분기함.

이 때 필요한 단계만 확인 후 분기하며, "기존 확장" 분기로 들어오면 Phase 선택 매트릭스에 따라 실행할 Phase를 결정함.
건너뛸 수 있는 Phase는 건너뛰고, 영향받는 범위만 실행함.

#### Phase 7-5 -- 운영, 유지보수 워크플로

Phase 0 이후 기존 내용을 유지 보수 하겠다 판단되면 7-5로 넘어가.

### 피드백 반영과 변경 이력 - drift를 방지하는 명확한 증거

- 7-1. 피드백 수집
  - 매 실행 완료 후 사용자에게 두 가지 질문을 던져봄
    - 결과에서 개선할 부분이 있나?
    - 에이전트 팀 구성이나 워크플로에 바꾸고 싶은 점이 있나?
- 7-2. 반영 대상 매핑
  - 받은 피드백을 유형에 따라 _어디에 반영할지_ 결정.
    - 유형: 결과물 품질
    - 유형: 에이전트 역할
    - 유형: 워크플로 순서
    - 유형: 팀 구성
    - 유형: 트리거 누락
- 7-3. 변경 이력 테이블이 진화의 명확한 증거다
  - CLAUDE.md 4개 항목 중 가장 소홀히 하기 쉬운게 변경 이력
  - 그러나 이는 단순 로그가 아니라, 하네스가 어떤 방향으로 진화했는지 추적하고 퇴행을 방지 하는 역할 함
  - 날짜, 변경 내용, 대상, 사유를 기록하며 마지막 "사유"는 특히 중요
    - 나중에 이 사유를 갖고 판단해서 지우거나 할 수 있게.
- 7-4. 진화를 촉발하는 세 가지 신호
  - 사용자가 요청하지 않아도 아래 신호들을 통해 하네스 개선을 고려해야 함
    - 반복 피드백
    - 반복 실패
    - (결정적) 우회 관찰
      - 사용자가 하네스를 호출하지 않고 직접 편집기를 연다는 것은 하네스가 제 기능을 못하고 있다는 가장 직접적인 증거.
      - 이 때 Agent에게 쓰라고 독려하는게 아니라, 왜 쓰지 않는가를 물어 description이나 워크플로를 고쳐야지.

### 재실행과 부분 재실행

앞 절이 '하네스 진화시키기'였다면, 이번 절의 주제는 진화시킨 하네스를 '어떻게 다시 실행하는가'.
다음은 오케스트레이터가 재실행을 올바르게 처리하게 해 주는 요령들.

- 요령 1. description의 재실행용 키워드
  - description에 "다시 실행", "재실행" 등 포함
  - description이 초기 실행, 후속 실행 모두 커버해야 함
- 요령 2. Phase 1 워크스페이스 확인
  - 워크스페이스 확인에 따라 다음 세 갈래로 분기
    - \_workspace/ 없음
    - \_workspace/ 존재 + 부분 수정 요청
    - \_workspace/ 존재 + 새 입력 제공
- 요령 3. 에이전트 재호출 지침
  - 이게 에이전트 레벨의 재진입성을 만듦

### 심화 - ADR과 Build to Delete

변경 이력표가 유지보수의 시작점이지만 하네스가 커지고 변경이 많이 누적되면 ADR(Architecture Decision Record)로의 확장을 고려할 수 있음.

이는 아키텍처 결정의 배경과 트레이드오프를 기록하는 문서로, 5개 필드로 구성됨.

1. 상태 - 활성/페기됨
2. 맥락 - 왜 이 결정이 필요했나
3. 결정 - 무엇을 정했나
4. 결과 - 어떤 트레이드오프를 받아들였나
5. (핵심) 삭제 조건 - 언제 이 결정이 불필요해지는가

ADR은 변경 이력표의 상위 호환이 아니라 **다른 계층의 도구**

Build to Delete는 사라져야 할 시점을 설계에 포함하는 원칙.
삭제 조건이 명시된 구성요소라면 깔끔하게 제거할 수 있음.
